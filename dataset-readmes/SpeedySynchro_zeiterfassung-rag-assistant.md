# Zeiterfassung Assistant

A RAG (Retrieval-Augmented Generation) assistant that answers questions about
the **Zeiterfassung** time-tracking application - a real internal project
with a backend (Node/Express/MongoDB) and a frontend (React) - by combining
the product backlog with the actual source code.

Built as the capstone project for the [LLM Zoomcamp 2026](https://github.com/DataTalksClub/llm-zoomcamp).

## Problem

New contributors (or the developer themselves, months later) need to answer
questions like *"how are vacation requests approved?"* or *"how does the
reminder email work?"*. The answer is scattered across product tickets and
several source files. This assistant retrieves the relevant tickets/files
and generates a grounded answer, citing which files back it up - instead of
grepping through the codebase by hand.

## Dataset

- `data/raw/backlog.txt` - the product backlog (tickets ZEIT-1 to ZEIT-7),
  split into one document per ticket.
- `data/raw/backend/` and `data/raw/frontend/` - the app's TypeScript source
  files (93 files: controllers, routes, models, services, React components,
  pages).

99 documents total. See `src/ingest.py` for how the raw files become
`data/documents.json`.

## Architecture

```
question
   |
   v
[retrieval: vector search over the 99 documents]   (src/vector_search.py)
   |
   v
[prompt: question + retrieved documents as context]  (src/rag.py)
   |
   v
[LLM: llama-3.1-8b-instant via Groq]
   |
   v
answer (cites source filenames)
```

## Retrieval evaluation

A ground-truth set of 299 question/expected-document pairs was generated by
asking an LLM, for every document, "what questions does this document
answer?" (`src/generate_ground_truth.py`). Two retrieval methods were then
compared on Hit Rate (is the right document in the top 5?) and MRR (how high
is it ranked?):

| Method | Hit Rate | MRR |
|---|---|---|
| Keyword search (minsearch) | 36.45% | 0.211 |
| **Vector search (multilingual embeddings)** | **41.14%** | **0.290** |

Vector search wins on both metrics and is used in the app. It also handles
non-English questions much better - the backlog mixes English and German,
and keyword search fails on cross-language queries that vector search
handles correctly (see `src/evaluate_retrieval.py` / `src/evaluate_vector.py`).

**Limitation:** both scores are modest in absolute terms. The embedding
model truncates input at ~128 tokens, so long source files lose content at
indexing time - a chunking strategy (splitting long files into overlapping
windows, as covered in the course) would likely improve this further.

## LLM evaluation

Two prompt variants were compared with an LLM-as-judge (`src/evaluate_llm.py`):
a strict "answer or say you don't know" prompt, and a variant additionally
asking for a concise answer that cites its source filenames. Both scored
100% "relevant" on a 10-question sample - a tie, not a clear winner. The
second variant was kept for the app because it is more useful in a UI
(shorter, verifiable answers), not because it scored higher.

## Interface

A Streamlit app (`src/app.py`): ask a question, get an answer, rate it
👍/👎. Run it locally or via Docker (see below).

## Monitoring

The main app logs every rated interaction (question, answer, rating, and
which documents were used) to `data/feedback.jsonl`. The `Dashboard` page
(`src/pages/1_Dashboard.py`) reads this log and shows:

1. Positive vs. negative feedback counts
2. Feedback over time
3. Answer length distribution
4. Retrieved document types (backlog vs. code)
5. Most frequently retrieved files
6. Positive rate by document type

`src/seed_feedback.py` populates this log with real interactions (real
questions run through the real pipeline, judged by an LLM) so the dashboard
has data to show out of the box.

## Tech stack

- **LLM**: Groq (`llama-3.1-8b-instant` for the app, chosen over the larger
  `llama-3.3-70b-versatile` after repeatedly hitting its 100k-tokens/day free
  tier limit during evaluation)
- **Retrieval**: `minsearch` (keyword) and `sentence-transformers` with
  `paraphrase-multilingual-MiniLM-L12-v2` (vector), compared and the latter
  kept
- **Interface**: Streamlit
- **Containerization**: Docker

## Running locally

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt

cp .env.example .env            # then fill in GROQ_API_KEY

python src/ingest.py            # builds data/documents.json
python -m streamlit run src/app.py
```

## Running with Docker

```bash
docker build -t zeiterfassung-rag-assistant .
docker run --env-file .env -p 8501:8501 zeiterfassung-rag-assistant
```

Then open http://localhost:8501.

## Reproducing the evaluation

```bash
python src/generate_ground_truth.py   # data/ground_truth.json
python src/evaluate_retrieval.py      # keyword search Hit Rate/MRR
python src/evaluate_vector.py         # vector search Hit Rate/MRR
python src/evaluate_llm.py            # LLM-as-judge prompt comparison
python src/seed_feedback.py           # populate data/feedback.jsonl
```

## Known limitations

- Retrieval scores (Hit Rate ~41%) leave room for improvement - chunking
  long source files would likely help.
- The LLM-as-judge evaluation used a small sample (10-20 questions) and the
  same model family for both generation and judging, which can bias results.
- `llama-3.1-8b-instant` is used in production instead of the larger model
  purely due to Groq's free-tier daily quota, not because it's the better
  model.
