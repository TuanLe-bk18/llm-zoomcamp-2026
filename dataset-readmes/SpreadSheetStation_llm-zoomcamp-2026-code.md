## 📋 Project Overview

### Problem Statement

Students and history enthusiasts often have questions about historical events like the Dancing Plague of 1518. Finding accurate answers from scattered online sources is time-consuming. This project solves that problem by building a specialized AI assistant that:

- Answers questions using a curated knowledge base
- Uses an agentic approach that searches multiple times to find the best answer
- Provides a clean web interface for asking questions and viewing responses
- Tracks user feedback and response times through a live dashboard

### Dataset

The knowledge base consists of 10 question-answer pairs about the Dancing Plague of 1518, covering:
- What happened (the outbreak itself)
- Causes and theories (psychogenic, ergotism)
- Death toll and fatalities
- Pop culture references (books, films)

## 🧠 Project Design & Justification

This section explains the design choices made throughout the project.

🔍 For a deeper critical dive, I recommend taking a look at the [Evaluation Criteria](./evaluationCriteria.md) page as well.

---

### Data Source

I used a relatively short Wikipedia article as my data source: **"Dancing plague of 1518"**.

- **Source:** [Wikipedia Article](https://en.wikipedia.org/wiki/Dancing_plague_of_1518)
- **Raw file:** `DataSource/WikiArticle.txt`
- **Chunking:** I manually chunked the article per paragraph by adding triple dashes `---` as separators.

This resulted in **5 chunks**, each with a unique `doc_id`:

| doc_id | Section |
|--------|---------|
| doc_001 | Dancing plague of 1518 - short summary |
| doc_002 | History Events |
| doc_003 | Veracity of deaths |
| doc_004 | Modern theories |
| doc_005 | Pop culture and media |

The chunks were extracted using a Jupyter notebook and saved as `dancing_plague_chunks.csv`.

---

### The QA Knowledge Base ("The FAQ")

For each chunk, I manually wrote **2 questions** using Google Sheets, creating a CSV file

This resulted in **10 Q&A pairs**, each with a unique `qa_id`:
qa_001 till qa_010

**File:** `DataSource/qa_knowledge_base.csv`

---

### Why Lexical Search?

I used **lexical (keyword) search** with minsearch instead of vector search.

**Reasons:**
- The dataset is small (only 5 chunks, 10 Q&A pairs).
- The Wikipedia article is short and straightforward.
- Lexical search is fast and works well for this scale.
- No need for embeddings or a vector database.

**Search index:** Built at startup using `fp_ingest.py` (swift and simple).

---

### Why Agentic RAG?

I decided to build an **agentic RAG** instead of a fixed pipeline.

| Aspect | Standard RAG | Agentic RAG |
|--------|--------------|-------------|
| Search runs | Once, with the exact user query | Multiple times, with refined queries |
| Control | Developer decides | LLM decides when and what to search |
| Flexibility | Fixed flow | Adaptive |

**Why agentic?**
- The LLM can reformulate queries if the first search returns poor results.
- It can make multiple searches and combine information.
- Evaluation showed it performed better (94% vs 90%).

**Implementation:** `agentic_assistant.py` using OpenAI's tool calling.

---

### Ground Truth Generation

To evaluate the system, I generated ground truth data.

**Process:**
1. Used an LLM to generate **5 new questions** for each of my 10 original Q&A pairs.
2. This created **50 ground truth questions**.
3. For each question, I knew which `qa_id` held the correct answer.

**File:** `GroundTruth/my_ground_truth.csv`

This ground truth was used for:
- Search evaluation (Hit Rate and MRR)
- LLM evaluation (RAG vs Agentic comparison)

---

### Retrieval Evaluation

I tested **6 different boost combinations** to find the best search configuration.

| Configuration | Hit Rate | MRR |
|---------------|----------|-----|
| Default (q=2.0, a=0.5) | 0.8400 | 0.6070 |
| Equal (q=1.0, a=1.0) | 0.9000 | 0.6413 |
| High Question (q=3.0, a=0.5) | 0.8200 | 0.5793 |
| **High Answer (q=1.0, a=2.0)** | **0.9000** | **0.6663** |
| Very High Question (q=5.0, a=0.5) | 0.8000 | 0.5433 |
| Very High Answer (q=1.0, a=4.0) | 0.8800 | 0.6430 |

**Winner:** `question=1.0, answer=2.0` → used in `fp_rag_helper.py`

**Script:** `search_evaluation.py`

---

### LLM Evaluation: Standard RAG vs Agentic RAG

I compared two approaches on the 50 ground truth questions:

| Approach | Good Answers | Score |
|----------|--------------|-------|
| Standard RAG (`fp_rag_helper.py`) | 45/50 | 90.0% |
| **Agentic RAG (`agentic_assistant.py`)** | **47/50** | **94.0%** |

**Winner:** Agentic RAG → used in `streamlit_app.py`

**Process:**
1. Generated RAG answers using `fp_rag_helper.py` → `GroundTruth/rag_answers.csv`
2. Generated Agent answers using `agentic_assistant.py` → `GroundTruth/agent_answers.csv`
3. Used an LLM judge to compare each answer against the original → `evaluate_judge.py`


#### Why CSV Instead of a Database?

For this capstone, I chose **CSV** over PostgreSQL for monitoring data.

| Reason | Explanation |
|--------|-------------|
| **Simplicity** | No Docker or database setup required – reviewers can run the app immediately |
| **Portability** | The `feedback.csv` file is self-contained and included in the repo |
| **Sufficient Scale** | With low expected traffic, CSV handles the data volume just fine |
| **Better Review Experience** | Peer reviewers see sample data and charts instantly without extra configuration |

While a database would be better for production-scale systems, the CSV approach is simpler, more reproducible, and fully meets the monitoring evaluation criteria for this project.

---

### Summary of Design Choices

| Component | Choice | Justification |
|-----------|--------|---------------|
| Search | Lexical (minsearch) | Small dataset, fast, simple |
| RAG Type | Agentic | LLM can refine queries; better results (94%) |
| Ground Truth | LLM-generated | 50 questions from 10 original Q&As |
| Interface | Streamlit | Simple, Python-based, easy for reviewers |
| Monitoring | CSV + Streamlit dashboard | No database setup needed; 5 charts |
| Containerization | Docker + start.sh | Easy setup for reviewers |
